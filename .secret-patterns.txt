# Secret patterns — one extended regex (ERE) per line, # for comments
# Block commits/pushes containing these patterns.
#
# Consumer 1: .githooks/pre-commit  (staged diff, per file)
# Consumer 2: .githooks/pre-push    (outgoing commits, -U0 patch stream)
# Consumer 3: .github/workflows/ci.yml job `secret-scan`
#             (scripts/security/scan_secret_patterns.sh over tracked files)
#
# DELIBERATELY NOT HERE: a bare-hex pattern such as [0-9a-f]{64}.
# keys.json legitimately carries published *deterministic* test vectors for the
# mcu (stm32/esp32/esp32s3) and sim devices, and crates/microfips-core/tests/
# golden_vectors.json is 64-hex by design. A blunt hex pattern here would either
# block every legitimate vector edit or need an allowlist wide enough to swallow
# the real leak (which is exactly how the leaked linux nsec stayed invisible).
# The host-key rule is enforced semantically instead — every device whose
# `type` is `fips-host` must have an `nsec_hex` shaped RETRIEVE_FROM_<HOST>:
#   scripts/security/check_keys_json.py        (the rule)
#   .githooks/pre-commit + .githooks/pre-push  (hooks)
#   .github/workflows/ci.yml job `secret-scan` (CI)

# Nostr private keys (bech32)
nsec1[a-z0-9]{20,}

# API keys (PPQ, OpenAI, etc.)
sk-[A-Za-z0-9]{10,}

# z.ai key format (32-char hex hash + dot + alphanumeric)
[0-9a-f]{32}\.[A-Za-z0-9]{8,}

# Private keys (PEM format)
-----BEGIN [A-Z ]*PRIVATE KEY

# Bearer tokens
Bearer [A-Za-z0-9._~+/-]{20,}

# Hardcoded password/secret assignments (not env vars)
password.*=.*['\"][^'\"]{4,}['\"]
api_key.*=.*['\"][^'\"]{8,}['\"]
secret_key.*=.*['\"][^'\"]{8,}['\"]

# Signal phone numbers
\+1[0-9]{10}

# Matrix access tokens
syt\.[A-Za-z0-9_-]{10,}
